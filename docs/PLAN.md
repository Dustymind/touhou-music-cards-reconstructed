## 1. 调研结论（为什么这么设计）

### 1.1 上游是什么

纯前端、无后端、无数据库的静态站：Next.js 16 App Router（全部 `"use client"`）+ React 19 + MUI 7 + PeerJS（WebRTC 数据通道做联机）。数据分四层：`public/*.json` 静态数据 → 内存 `GlobalData`/`GameJudge` → `localStorage` 7 个键 → PeerJS 事件。

玩法：把角色卡排进自己的牌库 → 放歌 → 抢拍对应角色的卡 → 抢对得牌/抢错罚牌。两种模式：**经典模式**（抢错要交牌，先清空牌库者胜）、**休闲模式**（抢错忽略，收牌多者胜）。支持单机练习 / 电脑对手 / 远程主机 / 远程客户端 / 观察者 / 多人混战。

### 1.2 上游必须继承的部分

- 完整对战规则（判定、罚牌 `givesLeft` 计算与夹紧、牌库转移、超时、终局条件）
- 22 种网络事件的语义与主机转发规则（只有主机转发，客户端永不转发）
- 全量快照 `SyncData` 的恢复模型
- 双方各自播放本地音频（不传音频字节，只传"当前角色 / 曲目 / 随机种子"）
- UI 结构与视觉（4 个页签、卡片状态色、字体、动效）
- 彩蛋：Alice 按钮、`?cheatcode=`（SHA-256 白名单）、`?g=`、`?r2=`、`?locale=`、蜂鸣倒计时

### 1.3 上游必须修掉的部分（重构的理由）

代码级缺陷（详见 `.ref/notes/A-*.md` §11、`B-*.md` §3.7）：

| 级别 | 缺陷 | 影响 |
|---|---|---|
| 高 | B2 远程经典模式超时产生负 `givesLeft` 时**死锁** | 回合无法推进 |
| 高 | B3 `syncNextTurn` 快照早于 `finishTurn` 的删牌 | 客户端残留幽灵卡 |
| 高 | B4 `applySyncData` 不校验 `cardStates` 长度 | TypeError 崩整棵树 |
| 高 | B1 `GameFinished` 状态从未被赋值，无终局判定 | 只能手动 Stop |
| 中 | B5 `give` 事件非幂等，丢一条永久串数 | 计数与终局判定双错 |
| 中 | B6 连接 close 处理 `index !== -1` 恒真 | 可能删错连接并抛错 |
| 中 | B7 观察者无法请求同步 | 观察者永远无法自愈 |
| 中 | B8 判定用各自本地音频起点的时间戳，而 `countdown` 从不同步 | 跨端判定不公平 |
| 中 | B9 无可用角色时卡死在 `TurnCountdownNext` | 死界面 |
| 中 | 音频层 12 项（`src=""`、依赖数组不含音源版本、随机起播种子全页固定、播放时长定时器不重装…） | 换源/换歌静默失效 |
| 低 | 存档无版本号、加载全有或全无、`cardCollection` 不持久化、角色改名静默丢档 | 用户设置无声丢失 |

数据级缺陷（详见 `.ref/notes/C-*.md`）：

| # | 事实 | 处置 |
|---|---|---|
| 1 | 347 条被引用曲目中 **1 条三表全缺**（八雲紫的 `Necro-Fantasia` 少写 `.mp3`） | 新 schema 用 `(专辑,曲目)`，从根上消除 |
| 2 | `sources_163.json` 有 1 条改名残留键（U+FF5E） | 迁移时删除 |
| 3 | `エタニティラルバ` 角色内重复一条曲目 | 迁移时去重 |
| 4 | **`card` 字段 116 字符串 / 5 数组**，`music` 25 字符串 / 96 数组 | 迁移统一为数组 |
| 5 | 子目录碟 **3 张专辑 5 个子目录**（Day/NightDisc、Arrange/OriginalDisc、Trance） | 拆成 5 个独立专辑名 |
| 6 | **306 条孤儿曲目**（源表有、无角色引用），其中 142 条是格斗作系统曲 | 规则归属 + 无法归属者单列（§11.1 Q4） |
| 7 | 8 条 R2 URL ≠ 前缀+键（曲名自带尾句号）；1 组 thbwiki URL 被两条键共用 | 迁移时实测并登记白名单/重取 |
| 8 | 2 条键非 NFC（`虹色のセプテントリオン` 内的分解假名） | 迁移时规范化 |

| 10 | 落盘的是**数组下标**，中间插曲会静默串歌 | 新模型落盘 `trackId`（字符串），下标语义彻底废除 |

### 1.4 v1/v2 工作区的教训（必须写进设计与测试）

1. 曲目字符串同时当显示名和 URL 表主键、两边手工维护、**零校验** → 一个字符的错永远播不出声。→ 新方案：单一真相源 + 生成 + 校验器 + CI 漂移检查。
2. `musicSelection` 存下标 → 数组顺序即协议。→ 新方案：稳定 `trackId`，顺序无关。
3. 越界/`-1` 下标在渲染路径抛错 → **白屏**。→ 新方案：解析器纯函数 + 边界守护 + 单元测试覆盖非法输入。
4. 存档全有或全无 + 角色改名丢档。→ 新方案：分键版本化 + 逐项校验 + 稳定 key 与显示名分离。
5. 在启动 effect 里多写一个 state 会抢在加载前覆盖存档（v2 踩过）。→ 新方案：持久化层显式初始化顺序 + 门控，并有回归测试。
6. 在 `useState` 初值里读 `window` 导致 hydration 不一致（v2 踩过）。→ 采用 Vite SPA，从架构上消除该问题类别。
7. 测试**必须双引擎**（chromium + firefox），音频断言必须轮询 `readyState` 而非固定 sleep，引擎结果不一致先怀疑测试代码。
8. 清理调试代码要手工 edit，不要用正则批量删（曾把文件改坏）。

## 2. 关键决策与理由

### D1 前后端：纯前端 SPA + 独立本地音乐助手（推荐）

**理由**

- 音频必须在玩家浏览器里播放（需求 4.2 亦如此），服务端无法代播；服务端能承担的只有"转发状态"。
- 上游的联机模型（主机权威 + 全量快照）已被证明能跑通，且本作是朋友间小规模对局，不需要匹配/排位/持久化战绩。
- 静态站可直接放本机或 GitHub Pages，无运维成本；本地音乐库天然在玩家机器上，远程后端反而够不着。
- 需求 4.1 的"本地源"本质是一个**本机 HTTP 服务**（要 CORS + Range），这跟"应用后端"是两件事，单独作为助手即可。

**代价与对策**

- P2P 在受限网络下可能打洞失败 → 传输层抽象（D9）+ 助手可在同一进程里兼作**信令/中继**（未来，接口先留）。
- `sources_163.json` 全是 `http://`，https 页面会被混合内容拦住 → 源开关里默认**关闭**网易云，或走助手代理（预留 `proxyable` 字段）。
- 主机权威下主机有延迟优势 → 保留上游"按反应时间判定"的口径，并在配置里提供"按到达顺序判定"选项（§8）。

**若你选择前后端分离**：我会改成两仓库（`web` + `server`），`server` 用 Node/TS 做权威房间（回合令牌由服务端签发、状态机在服务端、客户端只做渲染与输入），本地源由服务端代理。游戏核心写成**与运行位置无关的 reducer**，两种形态共用同一份规则实现 —— 这也是本方案无论如何都会预埋的接口。

### D2 前端框架：Vite + React 19 + TS + MUI 7（推荐）

- 上游 Next 只在 5 处产生框架耦合（`next/image`、`next/link`、`next/font/local`、`layout.tsx` 的 metadata），全部可替换，组件可近乎照搬。
- 应用 100% 客户端，Next 的 SSR/静态导出只带来额外机制与 hydration 风险（v2 已踩）。Vite 构建更快、调试更直白、GitHub Pages 直接可部署。
- 去掉 Tailwind（上游引入但**零工具类使用**），保留 MUI 主题 + `CssBaseline`，视觉不变而构建面更小。
- 字体沿用上游三个本地 TTF（Inconsolata 计时、Whitney 正文、YuGothic CJK 回退）。

### D3 工具链：pnpm + fnm（前端）／ uv + Python 3.13（数据与助手）

- 数据侧要读写 TOML、跑跨表比对、生成报告、起带 Range+CORS 的静态服务，Python 标准库 `tomllib` + 成熟的文本处理最省事；v2 的 `serve_local_music.py` 已被实测验证，可在其基础上改造而不是重写。
- 前端侧只用 pnpm；**生成物提交进仓库**，因此构建前端不需要 Python，只有"改数据"才需要。
- 若你更想要单一工具链，可把 `tools/` 改成 TS（`smol-toml` + node http），本地服务约 200 行可平移 —— 这是 §11.1 Q7。

### D4 仓库：单仓库 + 无上游 remote

- `git init`，不设 upstream remote；`.ref/`（上游只读副本与调研笔记）进 `.gitignore`。
- 提交规范：`<type>: <英文小写短句>`，`type ∈ feat|fix|data|docs|test|chore|refactor`，**一个逻辑改动一个 commit**，正文需折行时 ≤ 75 列，**不 push**。
- 里程碑见 §10，每个里程碑若干提交。

### D5 角色存储：一角色一 TOML + 稳定 key

```toml
# data/characters/kirisame-marisa.toml
key = "kirisame-marisa"     # 稳定 ID：存档 / 联机 / 预设 / 卡面索引都用它，永不随显示名变化
name = "霧雨魔理沙"          # 显示名，可改
order = 1                   # 默认播放顺序（把上游"JSON 插入序"显式化）
card = ["魔理沙.png"]
searchNames = ["霧雨魔理沙", "Kirisame Marisa", "雾雨魔理沙", "wuyu molisha"]
music = [
  ["東方永夜抄 ～ Imperishable Night", "恋色マスタースパーク", "角色曲"],
  ["幻想曲抜萃 ～ 東方萃夢想 Day Disc", "04. 恋色マジック", "角色曲"],
  ["全人類ノ天楽録 ～ 東方緋想天 Arrange Disc", "03. 星の器 ～ Casket of Star", "角色曲"],
  ["核熱造神ヒソウテンソク ～ 東方非想天則", "11. 恋色マジック", "角色曲"],
]
```

- **一角色一文件**：diff 可读、并行编辑不冲突；代价是需要显式 `order`（这反而修掉了上游"顺序即协议"的隐式耦合）。
- **`key` 与 `name` 分离**：直接修掉上游"角色改名 = 静默丢档"的真实事故（`绵月丰姬`→`綿月丰姬`）。
- 文件名 = `key`，因此含 `/` 的角色名（`ルナサ/メルラン/リリカ・プリズムリバー`）不再破坏路径。
- TOML 一律用基本字符串 `"…"`（曲名里有 11 条含 ASCII 单引号，字面量字符串会截断）。

### D6 曲目身份：`(专辑, 曲目)` 二元组

- 上游把 `"专辑/艺术家 - 曲名.mp3"` 同时当显示名和 URL 键，靠手抄一致，已产生 2 个真实故障。
- 新方案：曲目身份 = `(专辑, 曲目)`；`trackId = 专辑 + "\u0001" + 曲目`（仅内部用）。
- **`曲目` 定义为"专辑内标识串"**：剥掉 `<艺术家> - ` 前缀与 `.mp3`，但**保留 `NN. ` 曲目序号**。这不是风格问题而是数据逼出来的：`核熱造神ヒソウテンソク ～ 東方非想天則` 里有 `08. アンノウンＸ` 与 `18. アンノウンＸ` 两首同名不同曲，去掉序号就必然播错。界面显示时另派生"显示名"（去掉 `NN. `），与上游观感一致。
- **子碟拆成独立专辑名**（尊重原名，含空格）：
  | 原前缀/子目录 | 新专辑名 |
  |---|---|
  | `幻想曲抜萃 ～ 東方萃夢想/DayDisc` | `幻想曲抜萃 ～ 東方萃夢想 Day Disc` |
  | `幻想曲抜萃 ～ 東方萃夢想/NightDisc` | `幻想曲抜萃 ～ 東方萃夢想 Night Disc` |
  | `全人類ノ天楽録 ～ 東方緋想天/ArrangeDisc` | `全人類ノ天楽録 ～ 東方緋想天 Arrange Disc` |
  | `全人類ノ天楽録 ～ 東方緋想天/OriginalDisc` | `全人類ノ天楽録 ～ 東方緋想天 Original Disc` |
  | `東方神霊廟 ～ Ten Desires/Trance` | `東方神霊廟 ～ Ten Desires Trance Disc`（§11.1 Q8） |
- 拆碟同样是**必要条件**而非审美：不拆则 `全人類ノ天楽録` 内 4 组"同专辑同名曲目指向不同 URL"无法区分。拆碟 + 保留序号后，652 条源表条目得到 **652 个互异键、0 冲突**（已脚本验证）。
- 校验器强制：**被任何角色引用的 `(专辑, 曲目)` 在使用它的每张源表里必须唯一对应一个 URL**。

```
├─ albums.toml            # 专辑/游戏注册表：显示名、类别、pack、排序、碟归属、是否秘封

│  ├─ netease163.json     # [专辑, 曲目, URL] 数组，652 条
│  ├─ cloudflare_r2.json  # 651 条
│  └─ thbwiki.json        # 651 条
└─ registry.toml          # 数据版本号、生成器版本、校验白名单（已知例外）
```

`data/albums.toml` 片段：

## 5. 音乐源与 fallback（需求 4.1 / 4.2）

### 5.1 模型

```ts
type SourceDef = {
  id: "netease163" | "cloudflare_r2" | "thbwiki" | "local";
  label: { en: string; zh: string };
  tableUrl: string;        // 相对站根或绝对地址
  enabled: boolean;        // 【需求】开关，而不是单选
  order: number;           // 【需求】可调 fallback 顺序
  kind: "remote" | "local";
  proxyable?: boolean;     // 混合内容/跨域时可由助手代理（预埋）
};
```

- 持久化：`localStorage["tmc.v1.musicSources"]`（含 schemaVersion，未知字段忽略，损坏不回退整份存档）。
- 加载：并行拉取**所有已启用**源的源表（未启用不拉），逐个记录 `{status, count, error}`。
- 解析：`resolveUrl(track)` = 按 `order` 遍历已启用且加载成功的源，取第一个命中 `(专辑,曲目)` 的 URL。
- **运行时回退**：`<audio>` 的 `error` 事件 → 把 `(source, trackId)` 标记为失败 → 自动切换下一个源重试（同一次播放内最多重试 N 次）→ 全部失败才报"该曲目在当前音源组合下不可用"，并在配置页显示诊断。
- 配置页每个源一行：开关 + 上下移动（拖拽 + 按钮两种）+ 状态（已载入 N 首 / 失败原因）+ 试听按钮；另提供"全部启用/只留 R2"一键预设。

### 5.2 本地源（参考 v2 实现并优化）

- 助手服务（Python/uv）`tools/local_source.py`，在 v2 `serve_local_music.py` 基础上改造：
  - `GET /manifest.json` → 动态生成，格式与新源表一致（`[[专辑,曲目,URL]]`），并附曲包元信息（`pack = "otomads"`）；
  - `GET /media/<专辑>/<曲目>.mp3` → Range（206 + `Content-Range`）、CORS、`Accept-Ranges`；
  - 配置从 `local-source.toml` 读（`[server] host/port`、`[library] roots`、`[packs]`）；
  - 端口占用自动回退 + 打印实际地址；应用侧按 v2 的候选端口发现逻辑自动找到它。
- 界面：本地源地址输入框（默认 `http://127.0.0.1:8011/`）+ 「重新载入」+ 「已载入 N 首」+ 自动发现到的地址提示。
- **需求 4.2 的落法**：本方案下音频一律由前端下载播放；本地源由该助手直接提供（不经"应用后端"）。若你选择前后端分离，则改由服务端代理转发（接口已预留 `proxyable`）。

### 5.3 数据一致性校验（消灭上游"手抄键"问题）

- 被引用曲目在**每一张已发布源表**里的覆盖率报告（缺哪条、缺在哪张）；
- 孤儿曲目清单（按专辑分组）与"孤儿中与在用曲目只差标点"的近似重复告警；
- URL 形态检查（R2 = 前缀 + 专辑/曲目；163 = `id=`；thbwiki = hash 路径），已知例外走白名单；
- 抽查实链：带 `Range: bytes=0-4095` 的 GET，断言 `206`、`audio/mpeg`、头部 `ID3`（仅网络测试任务，可跳过）。

## 6. 选择系统（需求 5 / 6）

### 6.1 预设模型

```ts
type Extra = "角色曲" | "道中曲" | "更多道中曲" | "秘封曲";
type Tri = "unset" | "on" | "off";

type PresetState = {
  albums:   Record<string, boolean>;   // 所有非秘封专辑/游戏的勾选框
  hifuu:    { parent: boolean; albums: Record<string, boolean> };  // 秘封曲：父项 + 每碟子项
  category: Record<Exclude<Extra,"秘封曲">, Tri>;  // 三个无子项三态开关
};
```

**解析算法**（纯函数，单元测试覆盖全矩阵；按"最具体 → 最泛"求值，先命中者胜）：

```
resolve(char, album, title):
  L1 显式条目覆盖（当前只由「仅单曲模式」写入，模型预留更细粒度）
     专辑 scope 的条目覆盖 → 秘封碟 scope → 秘封组 scope → 类别 scope
  L2 父控件
     extra == "秘封曲"  → 返回 秘封碟复选[album]          # 父复选框是批量控制，不存值
     否则 sw = category[extra]
        "on"    → true    # 范围内显式启用，压过专辑勾选（P1-a）
        "off"   → false   # 范围内显式禁用，压过专辑勾选（veto）—— 三种方案下都成立
        "unset" → 下沉到 L3
  L3 专辑/游戏复选[album]                                # 默认：勾了就选
```

| 层 | 控件 | 取值 | 作用 |
|---|---|---|---|
| L1 | 条目级显式覆盖 | 启用/禁用 | 最高（仅单曲模式的手选走这里） |
| L2a | 秘封碟复选（12 个） | true/false | 决定全部 `秘封曲` 曲目 |
| L2b | 类别三态开关 = 已启用 | → true | **压过**专辑勾选：该类别全体启用（P1-a，已裁定） |
| L2c | 类别三态开关 = 已禁用 | → false | **压过**专辑勾选：该类别全体禁用（veto） |
| L2d | 类别三态开关 = 未配置 | → 下沉 | 交给专辑勾选 |
| L3 | 专辑/游戏复选 | true/false | 默认值 |

- 秘封曲父复选框**不存储自身状态**，只做批量开关；显示态由 12 个子项派生（全选/全不选/半选）。这样从根上不存在"父关子开、勾了没用"的不可达状态。
- 仅单曲模式关闭时：从该角色的可用曲目里**随机取一首**；取哪首由**主机在回合开始时决议并广播**（见 §8），保证跨端一致。

### 8.3 传输抽象（需求 0 的可扩展性 + D1 的备选）

```ts
interface Transport {
  role: "local" | "host" | "client" | "observer";
  myIndex: number;
  sendToHost(e: ClientEvent): void;
  broadcast(e: HostEvent, except?: number): void;
  onEvent(cb: (from: number, e: NetEvent) => void): () => void;
  onPeerChange(cb: (peers: PeerInfo[]) => void): () => void;
}
```

- `LocalTransport`（单机/CPU）、`PeerTransport`（PeerJS，默认）、`BroadcastChannelTransport`（同浏览器多标签，**用于确定性联机测试**）、`WsTransport`（预留：接后端权威服务端）。
- 规则层 `game/rules.ts` 是纯 reducer，不含任何网络/React 依赖 → 可用单测穷举，也可整体搬到服务端运行（前后端分离时的迁移成本≈0）。

### 8.4 必须复刻的协议细节

22 种事件的字段名与语义、主机 `except=sender` 转发、客户端/观察者永不转发、`syncStart` 携带 `rngSeed`、`broadcastPlayerNames` 单播 `yourIndex`、`notifyName` 握手、混战"共享牌库归属玩家 0"、`localStorage` 各自的键（新命名空间）等，见 `.ref/notes/A-game-core-spec.md` 的 Reimplementation checklist（我会逐条对照实现并写成测试）。
